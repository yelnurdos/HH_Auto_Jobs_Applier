## R1 — [P1] Потеря фильтров не останавливает поиск

Уверенность: 10/10.

Место: `src/job_manager/playwright_manager.py:646–654`, также `_set_keywords:674–686`, `_sync_search_url_after_page_size:1284–1291`.

Код, подтверждающий проблему:

```python
if query.get("text", [""])[0] != keywords:
    logger.warning(...)
```

После применения панели несовпадение ключевых слов лишь логируется. Регионы и остальные параметры конечной выдачи не сверяются. `SearchProbe._confirmed_filters()` копирует желаемые настройки, а не подтверждённые значения.

Воспроизведение: в существующем HTML-фикстуре заменить в `applyFilters()` добавление регионов на `p.delete('area'); p.delete('text');`, оставив чипы и флажки исправными. Передать текущие настройки с `show=None`, чтобы изолировать отправку панели. `set_advanced_search_params()` успешно завершается с адресом:

```text
https://hh.ru/search/vacancy?search_field=name&search_field=company_name&search_field=description
```

Последствие: основной бот продолжит поиск/отклики без запроса `data` и ограничений по городам. Это повторяет исходную проблему молчаливой потери настроек.

Что исправить:

- После отправки панели и после изменения размера страницы проверять фактически применённые условия. Для отсутствующего в URL параметра использовать наблюдаемое состояние интерфейса, не предположение.
- При несовпадении ключевых слов, регионов или заданных флажков — `SearchSetupError` до обработки вакансий. Сохранять адрес как рабочий только после проверки.
- Отчёт должен различать запрошенные и подтверждённые фильтры.
- Регрессии: пропали `text`, один/оба `area`, заданный флажок; потеря условий после смены размера. Ожидается явная ошибка, а не успешный поиск.

## R2 — [P1] Telegram снова включается до окончания проверочного запуска

Уверенность: 10/10.

Места: `src/job_manager/search_probe.py:225–227`; `scripts/verify_search.py:104–108`; установка блокировок только на строках 61–62 после чтения резюме на строке 52.

Код:

```python
# SearchProbe.run(), finally
self._restore_external_side_effects()

# verify_search.main(), после возврата из run()
if report.get("error"):
    logger.error(f"Ошибка проверки: {report['error']}")
```

На ошибке поиска `run()` возвращает отчёт, уже восстановив `AsyncTelegramSink.__call__`. Затем `logger.error` вызывает настоящий обработчик Telegram. Аналогично ошибки авторизации/инициализации до установки блокировки не защищены. При исключении во время сбора резюме после установки блокировки до `probe.run()` нет общего восстановления и отчёта.

Воспроизведение: заменить оригинальный `AsyncTelegramSink.__call__` счётчиком без сети; добавить экземпляр sink в Loguru; вызвать `probe.run()` с `SearchPageError` из `start_search`; выполнить итоговый `logger.error` как в скрипте. **Оригинальный sink вызван 1 раз**, несмотря на `telegram_messages_sent: 0`.

Что исправить:

- Одна область блокировки на весь жизненный цикл проверки: до первого обращения к браузеру/авторизации и до сохранения отчёта, итогового логирования и закрытия браузера.
- Восстановление в едином внешнем `finally` или контекстном менеджере, в том числе при ошибке чтения резюме и отмене.
- Не запускать/не оставлять отложенные задачи Telegram. Не подменять безопасность просто записанными нулями в отчёте.
- Проверять полный `verify_search.main()` с подменённой сетью: ошибка поиска, ошибка входа/резюме и ошибка закрытия; ни одного вызова настоящего отправителя. Состояние после выхода восстановлено.

```python
evaluation = self.gpt_answerer.job_is_interesting()
```

```json
{"status": "ok", "actual_model": "не получена (нет ответа LLM)", "error": null}
```

Что исправить:

- Не считать штатной оценкой ошибку вызова/разбора модели. Сделать явный сигнал сбоя для проверки, не ограничиваться сравнением текста русского сообщения.

- Отсутствие метаданных модели и подмена модели не должны подтверждать проверку Luna.
- Регрессии: отказ модели на первой/последней вакансии, сломанный структурированный ответ, успешный разбор контактов и затем неуспешная оценка. Статус не `ok`, частичные результаты сохранены.

### R1a — [P1] Идентификатор региона читается уже с другого элемента

Уверенность: 10/10. `src/job_manager/playwright_manager.py:998–1011,1093–1109`.

```python
clicked = options.nth(best_idx)
await self._robust_click(clicked, ...)
# после клика и паузы
qa = (await clicked.get_attribute("data-qa")) or ""
```

`Locator.nth()` заново ищет элемент при каждом обращении. Если после выбора города подсказки удаляются из DOM, этот индекс глобального списка `magritte-select-option-*` указывает на другой пункт либо отсутствует. В фикстуре подсказки только скрываются.

Воспроизведение: в `pickRegion()` после скрытия `area-suggest` очистить его `innerHTML`. Получено `_applied_area_ids == {'Астана': 20, 'Алматы': 20}`: прочитан id пункта размера страницы. Валидация падает с вымышленным id 20. Если другой элемент отсутствует, исключение глотается, id остаётся `None`, и `_set_area()` не добавляет город для последующей проверки.

Исправить:

1. Читать и проверять id подсказки **до клика**; после клика подтверждать выбранный чип.
2. Требовать подтверждённый id для каждого запрошенного города. Неполный словарь не должен давать успешную проверку.
3. Регрессии: подсказка удаляется; её индекс занимает другое меню; нет читаемого id; после выбора из URL пропадает город.

### R1b — [P2] Сломан селектор чтения флажков панели

Уверенность: 10/10. `src/job_manager/playwright_manager.py:696–700`.

```python
locator = self.page.locator(f"[data-qa='search-filter-search_field-value-{key}]")
```
